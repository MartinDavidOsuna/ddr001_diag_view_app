## Recorrido relevante

1. `AppController.syncCurrentCase` llama a `ensureRemoteSession`.
2. Sin vínculo/token remoto válido, ésta llama a
   `POST /api/v1/field-sessions/start` con nombre, email, teléfono,
   `client_app=ddr001_diag_view` y metadata de instalación.
3. Ese POST **no contiene el método, pulsos, resultados ni fotografías**.
4. El backend registra usuario/acceso/device/work session, emite y persiste
   tokens y auditoría. Sólo después devuelve las credenciales.
5. El motor consulta acceso, reúne el expediente, sube evidencias y envía el lote.

MANUAL y BLE están admitidos explícitamente en el contrato remoto. Un error
antes de completar autenticación puede bloquear cualquiera de los dos métodos.
Esto no equivale a haber reproducido un expediente BLE real en producción.

## Defecto confirmado de observabilidad

El inicio/refresh Field usa errores `application/problem+json`, con
`detail`, `title` y `requestId` en la raíz. La app `_decode` sólo consulta
`error.message` y `error.code` anidados; por eso pierde el detalle y muestra
`HTTP 500`.

El módulo funcional normalmente devuelve el formato anidado, incluso para un
500 (`An unexpected error occurred.`). Esta diferencia, junto con la ausencia
previamente observada de registros funcionales, refuerza la hipótesis de fallo
previo al envío. Un intermediario o un artefacto desplegado diferente también
podría devolver otro formato: el texto del botón no identifica por sí solo la
excepción interna ni la ruta exacta.

## Lo que falta para establecer la causa raíz

No hay evidencia para afirmar que falte la migración, que fallen permisos o que
un campo específico rompa SQL. Las tablas funcionales y la nulabilidad de crew
ya se habían observado presentes, por lo que no corresponde prescribir una
migración a ciegas. Tampoco corresponde cambiar HTTP por HTTPS, el modo de
medición o las muestras cerradas para tratar este 500.

La siguiente corrección diagnóstica de la app debe conservar ambos formatos
de error, código HTTP, operación y request ID sin registrar tokens, identidad
completa o cuerpos de fotos. Eso permite distinguir inicio/refresh, acceso,
evidencia y lote en el propio dispositivo. Para verificar una reparación del
servidor se requiere un ACK real del expediente; pruebas locales no lo sustituyen.

## Fallo localizado: renovación de sesión

El operador reportó en 1.7.3: `Pendiente · Renovación de sesión · HTTP 500 ·
An unexpected error occurred.`. Esto sustituye la hipótesis inicial de fallo
al iniciar sesión: ya existen credenciales y falla su renovación antes del envío.

Se reprodujo en el código de API 1.1.2: verifyRefresh deja escapar
JsonWebTokenError y el middleware lo convierte en 500. Tokens malformados,
firmados con otra clave o con nbf futuro producen ese error antes de SQL.
No se extrajo el token del Pixel; su defecto concreto no está certificado.

Fix API 1.1.3 convierte únicamente rechazos JWT en 401 INVALID_REFRESH_TOKEN.
Worktree: /Users/martino/DEV/ddr001_api_refresh_fix, rama
fix/refresh-invalid-token-401, basada en ce2fd46. Parche adjunto:
api-1.1.3-refresh-fix.patch. 366 unitarias, type-check, lint y build aprobados;
E2E TEST pasó login, renovación real, evidencias, sync y ACK. Sin despliegue.

La recuperación inmediata se verificó en 7 pruebas de auth Flutter: logout
limpia credenciales aunque refresh devuelva 500; relogin con la misma identidad
conserva el user ID y el expediente local. Cerrar sesión y entrar nuevamente
es una recuperación específica de este caso, no una solución general para 500.
La app 1.7.3 ya se recupera de un 401 mediante el flujo Field existente.

## Causa del 422 confirmada y corregida en 1.7.5+24

Lectura directa de la pantalla del Pixel: items[6..13].payload.pointId
invalid_string, doce más. En AppController la captura usa
`id: 'point-${evidence.id}'`. El serializer lo enviaba sin adaptar aunque
el contrato SQL/API exige UUID. El fixture previo sólo usaba UUID y no cubría
la identidad creada por la captura real: se agregó esa regresión.

ADR-028 define adaptación UUID v5 estable sólo de transporte y reparación
acotada del lote rejected antes de receipt. La API compartida permanece sin
cambios. Validación: 339 pruebas Flutter; rechazo legacy reproducido con el
validador API y aceptación del nuevo payload; TEST acepta MANUAL y BLE con
todos los ítems created/exists/accepted. Falta ACK productivo del expediente.
